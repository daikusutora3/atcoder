# 競プロライブラリスキル

このスキルの目的は、このリポジトリの `library/` を「提出に使いやすく、後で探しやすい形」で増やし、既存資産も優先して再利用することです。

## 最初にやること

1. `library/README.md` と候補カテゴリの `README.md` を読む。
2. 既存ライブラリで足りるか確認する。
3. 足りなくても、問題固有コードなのか、再利用価値の高い一般化可能な処理なのかを分ける。

再利用価値が高いなら `library/` に切り出す。問題固有なら `src/...` 側に留める。

## 実装前の調査

新規ライブラリを作るときや既存ライブラリを大きく直すときは、実装前に必ずウェブで調べる。ローカルの実装だけを見てすぐ書き始めない。

調べる対象:

- 同種アルゴリズムの標準的なインターフェース
- 計算量、前提条件、典型的な落とし穴
- Python 実装での性能上の注意
- 可能なら AC Library、cp-algorithms、公式ドキュメントのような一次寄りの資料

調査結果は作業内容に反映し、説明では短く触れる。

- 何を参考にしたか
- その結果、どういう API や実装方針にしたか
- どの落とし穴を避けたか

## 調査時の観点

- 入力前提を明確にする。0-indexed か、自己ループや多重辺を許すか、連結性が必要かを曖昧にしない。
- 制約外入力や未対応ケースを黙って飲み込まない。対応範囲を明示する。
- Python では再帰の深さや定数倍が詰まりやすい。深い DFS は反復実装のほうが安全なことが多い。
- 見かけ上 `O(log n)` に見えても、実際には挿入が `O(n)` のような操作がある。計算量を実装に即して確認する。
- 提出時に貼りやすい単純な API を優先し、過度な抽象化は避ける。

## 既存ライブラリを使うとき

既存の `.py` と対応する `.md` を読んで、次だけ確認する。

- 入力形式が問題に合うか
- 出力形式がそのまま使えるか
- 計算量が制約内か

足りるなら再利用を優先する。軽微な一般化で済むなら、解答側で無理に分岐を足すよりライブラリ改善を検討する。

## 新規ライブラリを追加するとき

追加は次を 1 セットで行う。

- `library/<category>/<name>.py`
- `library/<category>/<name>.md`
- `library/<category>/README.md`
- 必要なら `library/README.md`

実装方針:

- 提出へ貼りやすい形を優先する。原則は短い関数 API だが、数行から十数行の典型処理で、問題ごとに初期値・境界・変数名を直接調整するほうが自然なら、関数化せずコピペ用スニペットとして置く。
- クラスが本当に有利でない限り関数中心で書く。
- 参照元の `src/...` に短い前処理や数行の定型処理として書かれているものは、まず同じ粒度で残すことを考える。関数化して呼び出すより、貼った後に `ok`、`ng`、`ans`、判定関数名などをその場で変えるほうが読みやすい処理はスニペットにする。
- ユーザーが「普通に〇〇するだけ」「関数一つだけでいい」など単純さを求めている場合は、最小 API に寄せる。追加機能は Markdown の発展例にも入れすぎない。
- ユーザーが「そのままコピペして使いたい」「関数化しないで」「めちゃくちゃシンプルに」などの意図を示したら、`.py` には import して使う部品ではなく、貼り付ける完成形の処理を書く。対応する `.md` でも `Functions` ではなく `Snippet` を中心に説明する。
- 問題固有の事情はできるだけ外に出し、汎用部分だけを残す。
- 計算量と入力前提が説明しやすい形に整える。

## API と変数名の決め方

- 競プロの提出コードに貼る前提なので、内部変数と Usage の変数名は短く、ただし意味が追えるものにする。
- 返り値が複数ある関数では、長すぎる説明的名前より、競プロで読みやすい短い名前を優先する。例: 座標圧縮なら `comp`、`vals`、`idx`。
- ただし 1 文字だけで意味が崩れる名前は避ける。`a` や `g` のような入力例の定番名はよいが、返り値説明では `idx` や `dist` のように役割が残る名前にする。
- 既存の解答に `i2v`、`v2i` のような対応関係がある場合は、その意図を保ちつつ、Usage ではユーザーがそのまま貼れる名前に整える。

## Markdown の最小構成

対応する `.md` には最低限これを書く。

- `Summary`: 何をするか、入力前提、注意点
- `Functions` または `Snippet`: 関数 API なら入出力と計算量、コピペ用なら貼るコード・前提・最終的に得られる変数・計算量
- `Usage`: 最小の使用例
- `References`: 参考にした記事や公式資料
- `Related`: 関連する ABC 問題と自分の解答へのリンク

Markdown は「使うための索引とメモ」であり、API 設計の押し売りではない。Summary は短くする。入力前提は重要なものだけを書く。返り値の説明では、入力列と、重複除去済みの補助リストのような派生データを混同しない。

README は「後で見つけるための索引」なので、追加したら必ず更新する。

`References` には、実装前の調査で実際に参考にした記事やドキュメントを入れる。URL を並べるだけでなく、そのライブラリで何を参考にしたのかが分かる形にする。

`Related` には、少なくとも次を入れる。

- 関連する AtCoder の問題名や問題 URL
- このリポジトリ内の自分の解答ファイルへのリンク

自分の解答ファイルへのリンクは必ず相対パスで書く。`../../src/abc456/e.py` のように、この `.md` から辿れる形にする。絶対パスや環境依存パスは使わない。

## 出力時に添える説明

このスキルを使って作業したら、結果説明には最低限次を含める。

- 既存再利用か新規追加か
- 採用した API
- 計算量
- 実装前に見たウェブ資料と、そこから反映した点
- `References` と `Related` に何を追記したか

## 例

入力: 「有向グラフの閉路検出を今後も使い回したい」

期待する動き:

- まず `library/graph/` を確認する
- 足りなければウェブで標準的な実装と落とし穴を調べる
- `library/graph/<name>.py` と `.md`、README をまとめて整える

入力: 「この木処理は今後も何度も使いそうなのでライブラリ化したい」

期待する動き:

- 既存ライブラリの有無を確認する
- 再利用価値が高ければ一般化して切り出す
- 調査で確認した前提条件や計算量を Markdown に残す
