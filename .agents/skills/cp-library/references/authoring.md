# 実装とドキュメントの指針

新規追加、API・アルゴリズムの改修、使い方の説明整備で必要な箇所を参照する。

## 設計・調査

既存の実装と説明を出発点にする。新しいアルゴリズムや、前提・計算量・Python での性能に不確かな点がある場合は、実装前に AC Library、原著、公式ドキュメントなどの資料で確認する。既存部品の利用や説明だけの修正で、一律に調査をやり直す必要はない。

設計に影響する条件を確認する。例えばグラフでは添字・自己ループ・多重辺・連結性、探索では境界と判定条件がある。対応範囲を説明し、制約外入力のために不要な防御コードを増やさない。

Python では深い再帰や定数倍に注意する。計算量は実装に即して記載する（例: 二分探索が `O(log n)` でもリストへの挿入は `O(n)`）。

## 実装の粒度

- 関数・クラスは、必要な入出力と操作に絞る。追加機能や発展例は依頼の用途に必要なものだけにする。
- 数行の前処理や、`ok`・`ng`・判定関数などを問題ごとに直接調整する処理は、元の粒度を保ったスニペットが適する。「関数化しないで」「そのままコピペしたい」という指定なら `.py` には貼る処理を書き、`.md` には調整箇所と結果の変数を説明する。
- 変数名は短く意味が追えるものにする。入力例の `a`・`g`、返り値の `idx`・`dist`・`comp`・`vals` など、競プロで読みやすい名前を使う。元の対応関係や既存 API の意味を保つ。

## 同名 Markdown

近くのライブラリの書式に合わせ、以下を短くまとめる。

| 項目 | 内容 |
| --- | --- |
| `Summary` | 用途、重要な入力前提と注意点 |
| `Functions` または `Snippet` | API の入出力、または貼るコード・調整箇所・得られる変数。いずれも計算量を記載 |
| `Usage` | 最小の使用例。入力と派生データを区別し、実装と一致させる |
| `References` | 実際に参照した資料と、設計・前提など何を参考にしたか |
| `Related` | 関連する AtCoder 問題と、このリポジトリ内の自分の解答 |

`Related` の解答リンクは `.md` から辿れる相対パスにする（例: `../../src/abc456/e.py`）。実在する問題・解答・資料だけを載せ、見つからない場合はその旨を記す。項目を埋めるために無関係なリンクを追加しない。

新規追加時はカテゴリ README に用途の分かる索引を加える。改修時は API・前提・計算量・使用例のうち変わる箇所を更新し、索引の変更は名前・用途・配置が変わる場合に限る。

## 確認と報告

新規実装やアルゴリズム変更は、用途に応じて使用例、境界ケース、小規模な愚直解との比較などで確認する。スニペットは貼り付け先の変数を用意して実行する。説明だけの修正は、実装との整合性とリンクを確認する。

調査した場合は参考資料と採用した点を、検証した場合は確認内容と限界を簡潔に伝える。変更していない項目の報告を増やさない。
