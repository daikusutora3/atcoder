# 実装指針

## 再利用する範囲と形

既存の API が目的に合うかを先に確認する。軽い一般化で済むなら既存実装の改善を検討し、呼び出し元への影響も確かめる。

提出へ貼った後の使いやすさを基準に形を選ぶ。

- 短い関数 API を基本とする。状態管理が自然なデータ構造などはクラスを使う。
- 数行から十数行の定型処理で、初期値・境界・判定関数名を問題ごとに調整するなら、元の粒度を保ったコピペ用スニペットが適している。
- 「関数一つだけ」「そのままコピペ」「関数化しないで」などの指定があれば、その形で完成させる。指定のない追加機能や発展例を増やしすぎない。

問題固有の入力処理や条件は外に出す。内部変数と使用例には、`g`、`dist`、`comp`、`vals`、`idx` など短く役割の分かる名前を使い、元コードの対応関係も保つ。

## 仕様と性能

対象のアルゴリズムに関係する前提を明確にする。例えばグラフなら添字、自己ループ・多重辺、連結性、重みの制約を確認する。未対応ケースは説明に残し、制約外入力への検査は必要性に応じて選ぶ。

計算量は実際の操作から判断する。二分探索を使っていても、Python のリスト挿入は線形時間になる。深い DFS では反復実装を検討し、再帰の深さと定数倍にも注意する。

ユーザーが調査を求めた場合や、仕様・計算量・Python の挙動に不確実性がある場合は、AC Library や Python 公式ドキュメントなどの一次資料を確認する。既存実装・説明で判断できる変更に、形式的なウェブ調査を追加する必要はない。実際に使った資料と、設計に反映した点を同名 Markdown に残す。

## 動作確認

変更した動作を確かめる最小の使用例と、アルゴリズム固有の境界ケースを選ぶ。複雑な処理は、必要なら小さな入力で愚直解と比較する。スニペットは必要な入力や判定関数を与えて、貼り付けた形で実行できることを確認する。
